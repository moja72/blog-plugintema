# PluginTema — Terminologia WordPress

> Este arquivo padroniza nomenclatura, capitalização, traduções, termos técnicos e escolhas linguísticas usadas no Blog PluginTema.
>
> Ele deve ser usado em conjunto com:
>
> - `VOZ_EDITORIAL.md`
> - `POSICIONAMENTO_EDITORIAL.md`
> - `ESTRUTURA_DE_ARTIGOS.md`
> - `CHECKLIST_DE_PUBLICACAO.md`
> - `REGRAS_DE_PESQUISA.md`
> - `POLITICA_EDITORIAL.md`
> - `DIRETRIZES_DE_SEO.md`
> - `REVIEWS_E_COMPARATIVOS.md`
>
> Princípio central:
>
> **usar o nome que o leitor reconhece, sem sacrificar precisão técnica.**

---

# 1. Regra geral de terminologia

Quando houver dúvida entre:

- tradução literal;
- termo oficial;
- termo usado pela comunidade;
- termo em inglês;

seguir esta prioridade:

1. nome oficial atual do produto ou recurso;
2. tradução oficial ou amplamente consolidada em PT-BR;
3. termo mais reconhecido pela comunidade brasileira;
4. termo original em inglês quando a tradução causar ambiguidade.

---

# 2. Primeira ocorrência

Quando um termo técnico em inglês for importante e puder gerar dúvida:

usar:

> **termo em PT-BR + termo original entre parênteses**

Exemplo:

> ambiente de staging (homologação)

ou, quando o inglês for mais reconhecido:

> staging (ambiente de homologação)

Depois da primeira ocorrência, usar apenas o termo padronizado.

---

# 3. Não traduzir nomes próprios

Nunca traduzir nomes oficiais de produtos, empresas ou marcas.

Correto:

- WordPress
- WooCommerce
- Elementor
- Elementor Pro
- Rank Math
- Yoast SEO
- WP Rocket
- LiteSpeed Cache
- Cloudflare
- Automattic
- Gutenberg
- Bricks
- Divi

Incorreto:

- “Elemento Pro”
- “Comércio Woo”
- “Foguete WP”

---

# 4. WordPress

Forma obrigatória:

> **WordPress**

Sempre com:

- W maiúsculo;
- P maiúsculo.

Nunca usar:

- Wordpress
- wordpress
- Word Press
- WPpress

---

# 5. Abreviação “WP”

“WP” é permitida quando:

- faz parte do nome oficial de um produto;
- aparece em código;
- aparece em domínio;
- o contexto técnico já está claro.

Exemplos:

- WP-CLI
- WP Rocket
- WP_Query
- wp-admin
- wp-config.php

Em texto editorial comum, preferir **WordPress**.

---

# 6. WordPress.org e WordPress.com

Manter exatamente:

- **WordPress.org**
- **WordPress.com**

Não tratá-los como sinônimos.

Quando a diferença for relevante:

- WordPress.org → projeto/software/ecossistema e site oficial;
- WordPress.com → serviço hospedado da Automattic.

---

# 7. WordPress Core

Forma preferida em texto técnico:

> **WordPress Core**

ou:

> **núcleo do WordPress**

Usar “WordPress Core” quando:

- falar de desenvolvimento;
- diferenciar Core de plugins/temas;
- citar tickets, APIs ou mudanças internas.

Usar “núcleo do WordPress” quando a frase ficar mais natural para público geral.

Evitar:

> Core

sozinho, quando puder ficar ambíguo.

---

# 8. “Core” em maiúscula ou minúscula

Quando fizer parte da expressão editorial padronizada:

> WordPress Core

Quando usado genericamente em português:

> núcleo do WordPress

Não alternar aleatoriamente entre “core”, “Core” e “núcleo”.

---

# 9. Plugin

Forma singular:

> **plugin**

Plural:

> **plugins**

Não usar:

- plug-in;
- plug ins;
- plugin's;
- plugins WordPress como construção automática em toda frase.

Exemplo natural:

> plugins para WordPress

---

# 10. Plugin oficial

Só chamar algo de “plugin oficial” quando existir vínculo oficial real com:

- WordPress;
- WooCommerce;
- fabricante;
- projeto.

Não usar “oficial” apenas porque está no diretório WordPress.org.

---

# 11. Plugin gratuito

Preferir:

> versão gratuita

ou:

> plugin gratuito

Não usar “free” sem necessidade.

Se o nome do plano for oficialmente “Free”, pode manter.

---

# 12. Plugin premium

“Premium” é permitido e reconhecido.

Mas, quando houver preço:

preferir explicar:

> versão paga

quando isso for mais claro.

---

# 13. Add-on

Forma preferida:

> **add-on**

Plural:

> **add-ons**

Quando o público for iniciante, primeira ocorrência pode ser:

> add-on (extensão)

Não usar:

- addon
- add on

a menos que faça parte de nome oficial.

---

# 14. Extensão

“Extensão” pode ser usada quando:

- o fabricante usa esse termo;
- o contexto não exige “add-on”.

Para WooCommerce, muitas integrações são chamadas de extensões.

Não forçar uniformidade quando o nome oficial divergir.

---

# 15. Tema

Usar:

> **tema**

Plural:

> **temas**

Evitar “template” como sinônimo de tema.

Um tema e um template são conceitos diferentes.

---

# 16. Tema clássico

Usar:

> **tema clássico**

Para temas que seguem a arquitetura tradicional do WordPress e não usam blocos para toda a estrutura do site.

---

# 17. Tema de blocos

Forma preferida:

> **tema de blocos**

É o termo para um tema construído para usar blocos também em áreas estruturais do site.

Evitar:

- tema FSE;
- tema Gutenberg;

como padrão editorial.

Podem aparecer em contexto histórico ou comunitário, desde que explicados.

---

# 18. Template

Usar:

> **template**

quando estivermos falando do conceito técnico de template do WordPress.

Exemplos:

- template de post;
- template de arquivo;
- template de página.

Não usar “template” como sinônimo genérico de:

- tema;
- layout inteiro;
- site.

---

# 19. Template part

Forma preferida:

> **parte de template**

Na primeira ocorrência técnica, pode usar:

> parte de template (*template part*)

Exemplos:

- cabeçalho;
- rodapé;
- área estrutural reutilizável.

---

# 20. Editor de Blocos

Forma editorial preferida:

> **Editor de Blocos**

É o editor usado para criar e editar conteúdo com blocos.

Depois da primeira ocorrência, pode usar:

> editor de blocos

em minúsculas quando não estiver tratando como nome da interface.

---

# 21. “Gutenberg” não é o nome padrão do editor

Evitar chamar automaticamente o Editor de Blocos de:

> Gutenberg

Usar “Gutenberg” quando estivermos falando de:

- projeto Gutenberg;
- plugin Gutenberg;
- desenvolvimento experimental;
- histórico da transição do editor;
- nomenclatura usada por uma fonte que precise ser discutida.

Para o leitor comum:

> Editor de Blocos

é preferível.

---

# 22. Gutenberg

Quando usado corretamente:

> **Gutenberg**

Nunca:

- Gutemberg
- gutenberg

---

# 23. Plugin Gutenberg

Quando falar do plugin experimental:

> **plugin Gutenberg**

Deixar claro que ele não é simplesmente “o WordPress”.

O plugin pode incluir funcionalidades antes de chegarem ao Core.

---

# 24. Editor Clássico

Usar:

> **Editor Clássico**

quando estiver falando da experiência anterior baseada principalmente no TinyMCE.

Se estiver falando do plugin:

> plugin Classic Editor

quando o nome oficial importar.

---

# 25. Editor do Site

Forma preferida:

> **Editor do Site**

É a interface usada para editar a estrutura global de um site com tema de blocos.

Pode incluir:

- templates;
- partes de template;
- estilos;
- navegação;
- páginas;
- padrões.

Não confundir com Editor de Blocos.

---

# 26. Editor de Blocos x Editor do Site

Regra:

## Editor de Blocos

Edita conteúdo de posts e páginas com blocos.

## Editor do Site

Edita a experiência global do site com tema de blocos.

Essa diferença deve ser preservada em todos os artigos.

---

# 27. Site Editing

Quando o conceito geral precisar ser mencionado, preferir:

> **Edição do site**

Se a fonte oficial usar “Site Editing” e isso for relevante:

> Edição do site (*Site Editing*)

---

# 28. Full Site Editing

“Full Site Editing” e “FSE” podem aparecer em:

- contexto histórico;
- documentação antiga;
- discussão técnica;
- citações;
- comparação de evolução do projeto.

Mas não devem ser a nomenclatura padrão da PluginTema para a interface atual.

Preferir:

- Editor do Site;
- Edição do site;
- tema de blocos.

---

# 29. FSE

Se for necessário usar a sigla:

primeira ocorrência:

> Full Site Editing (FSE)

Depois:

> FSE

Não usar a sigla sem explicação em artigo para público geral.

---

# 30. Bloco

Usar:

> **bloco**

Plural:

> **blocos**

É a unidade de conteúdo ou interface do sistema de blocos.

Exemplos:

- bloco de Imagem;
- bloco de Parágrafo;
- bloco de Navegação;
- bloco Query Loop.

---

# 31. Nome de blocos

Quando nos referirmos a um bloco específico da interface:

usar maiúscula inicial quando ajudar a indicar o nome do bloco.

Exemplo:

> bloco de Navegação

> bloco de Imagem

> bloco de Consulta

Se o nome oficial da interface brasileira divergir, priorizar o nome exibido no WordPress PT-BR.

---

# 32. Block Inserter

Forma preferida:

> **Inseridor de blocos**

Quando o termo técnico original importar:

> Inseridor de blocos (*Block Inserter*)

---

# 33. Padrão de blocos

Usar:

> **padrão de blocos**

ou simplesmente:

> **padrão**

quando o contexto estiver claro.

Não traduzir como “pattern” em texto comum.

---

# 34. Pattern

Manter “pattern” apenas quando:

- estiver em código;
- for nome de API;
- estiver citando documentação técnica;
- o termo original for necessário para pesquisa.

---

# 35. Padrão sincronizado

Usar:

> **padrão sincronizado**

para o recurso atual correspondente ao antigo conceito de bloco reutilizável sincronizado.

---

# 36. Bloco reutilizável

“Bloco reutilizável” deve ser tratado como nomenclatura anterior/legada quando aplicável.

Em conteúdo atual, preferir:

> padrão sincronizado

Quando houver risco de confusão:

> padrão sincronizado, anteriormente chamado de bloco reutilizável

---

# 37. Estilos globais

Usar:

> **Estilos globais**

Quando a referência for à funcionalidade/interface:

> Estilos

pode ser usado se esse for o rótulo atual da interface.

---

# 38. Global Styles

Manter inglês apenas em:

- APIs;
- documentação técnica;
- código;
- citação.

No texto editorial:

> estilos globais

---

# 39. Variação de estilo

Usar:

> **variação de estilo**

Não confundir com:

- estilo de bloco;
- variação de bloco.

---

# 40. Estilo de bloco

Usar:

> **estilo de bloco**

quando o recurso muda a apresentação de um bloco específico.

---

# 41. Navegação

Quando falar do bloco:

> bloco de Navegação

Quando falar do conceito:

> navegação do site

Evitar usar “menu” e “bloco de Navegação” como se fossem exatamente a mesma coisa em todos os contextos.

---

# 42. Query Loop

Para conteúdo técnico ou avançado, usar:

> **Query Loop**

Na primeira ocorrência para público geral:

> bloco Query Loop, usado para criar listagens dinâmicas de conteúdo

Se a tradução oficial do WordPress PT-BR estiver clara na interface alvo, usar a tradução exibida nela.

---

# 43. WP_Query

Nunca traduzir.

Usar exatamente:

> `WP_Query`

Com formatação de código quando possível.

---

# 44. Shortcode

Forma preferida:

> **shortcode**

Plural:

> **shortcodes**

Pode explicar na primeira ocorrência:

> shortcode, um pequeno código entre colchetes usado para inserir conteúdo ou funcionalidade

Não usar “código curto” como padrão editorial.

---

# 45. Widget

Usar:

> **widget**

Plural:

> **widgets**

É termo consolidado no ecossistema.

Não traduzir para “componente” automaticamente.

---

# 46. Sidebar

Em conteúdo para usuários:

> **barra lateral**

Em contexto técnico de temas:

pode usar:

> sidebar

quando estiver falando da estrutura registrada pelo tema.

---

# 47. Dashboard

Forma preferida para público geral:

> **Painel do WordPress**

Pode usar:

> painel

depois.

“Dashboard” é permitido quando:

- aparece no nome oficial;
- a interface está em inglês;
- o contexto técnico exige.

---

# 48. wp-admin

Usar:

> `wp-admin`

quando se referir especificamente à área administrativa ou caminho técnico.

Exemplo:

> acesse o `wp-admin`

Não usar “wp-admin” como sinônimo obrigatório de qualquer painel.

---

# 49. Admin

Em texto editorial, preferir:

- painel;
- área administrativa;
- administrador;

conforme o contexto.

“Admin” pode aparecer em contexto técnico.

---

# 50. Front-end

Forma padronizada:

> **front-end**

Não alternar com:

- frontend;
- front end;

a menos que faça parte de nome oficial ou código.

---

# 51. Back-end

Forma padronizada:

> **back-end**

Não alternar com:

- backend;
- back end;

a menos que faça parte de nome oficial ou código.

---

# 52. Interface

Preferir:

> **interface**

em vez de “UI” em texto para público geral.

“UI” pode ser usada em artigos técnicos, após contexto.

---

# 53. UX

Primeira ocorrência quando necessário:

> experiência do usuário (UX)

Depois:

> UX

Não usar “UX” apenas como adjetivo vago para dizer que algo “parece bonito”.

---

# 54. Page builder

Forma preferida na primeira ocorrência:

> **construtor de páginas (*page builder*)**

Depois, escolher uma das formas conforme o artigo.

Em artigos voltados à comunidade WordPress avançada, “page builder” pode ser mantido diretamente.

---

# 55. Construtor visual

“Construtor visual” pode ser usado quando descrever melhor a ferramenta.

Não tratar automaticamente:

- page builder;
- site builder;
- theme builder;

como sinônimos perfeitos.

---

# 56. Theme Builder

Quando for nome de recurso oficial de produto, manter:

> **Theme Builder**

Exemplo:

> Elementor Theme Builder

Não traduzir nome oficial.

---

# 57. Site builder

Pode ser traduzido como:

> construtor de sites

quando genérico.

Se fizer parte do nome oficial de produto, manter o original.

---

# 58. Multisite

Forma preferida:

> **WordPress Multisite**

Depois:

> Multisite

Usar maiúscula quando se referir ao recurso.

---

# 59. Rede Multisite

Forma preferida:

> **rede Multisite**

Evitar:

> instalação multisite

quando a intenção for especificamente a rede, embora “instalação Multisite” seja aceitável tecnicamente em certos contextos.

---

# 60. Site da rede

Preferir:

> **site da rede**

quando falar de um site individual dentro de uma rede Multisite.

Evitar “subsite” como termo padrão, pois pode sugerir hierarquia técnica que nem sempre existe.

“Subsite” pode ser usado apenas quando ajudar a explicar linguagem comum.

---

# 61. Site principal

Em Multisite:

> **site principal**

quando for de fato o site principal da rede.

Não confundir com:

- domínio principal;
- página inicial;
- site comercial.

---

# 62. Super Admin

Quando falar da função específica do Multisite:

> **Super Admin**

ou:

> superadministrador

Escolher conforme a interface/documentação utilizada e manter consistência no artigo.

---

# 63. Staging

Forma preferida:

> **staging**

Na primeira ocorrência para público menos técnico:

> staging (ambiente de homologação)

Depois:

> staging

Não usar:

- stage;
- ambiente teste

como substituto automático.

---

# 64. Produção

Usar:

> **produção**

Exemplos:

- ambiente de produção;
- site em produção.

Evitar “production” em texto PT-BR sem necessidade.

---

# 65. Desenvolvimento

- local;
- dev;
- desenvolvimento;

podem aparecer em contexto técnico.

# 66. Ambiente local

> **ambiente local**

> desenvolvimento local

---

# 67. Cache

# 68. Cache de página

# 69. Cache de objeto

Depois de escolher um termo:

não alternar sem razão.

Exemplo ruim:

- construtor de páginas;
- page builder;
- criador de página;
- builder;

todos no mesmo artigo para a mesma coisa.

Escolher um principal.

---

# 262. Regra de precisão acima de variedade

Não trocar palavra técnica por sinônimo apenas para “não repetir”.

Repetição controlada é melhor que imprecisão.

---

# 263. SEO não muda nomenclatura oficial

Se uma keyword estiver escrita incorretamente ou usar nomenclatura antiga:

não reproduzir o erro como padrão editorial.

Pode mencionar a variação se ajudar busca ou compreensão.

Exemplo:

> WordPress Multisite — também pesquisado por alguns usuários como “WordPress multi site”

sem adotar a forma errada.

---

# 264. Termos com marca registrada

Usar o nome correto da marca.

Não é necessário inserir `™` ou `®` em texto editorial comum, salvo necessidade jurídica ou citação oficial.

---

# 265. Código e interface têm prioridade literal

Em tutoriais:

se o botão diz:

> Save Changes

não rebatizar como:

> Confirmar configurações

Se a interface estiver em inglês, reproduzir literalmente e traduzir ao lado quando necessário.

---

# 266. Regra para screenshots

O texto deve usar a mesma nomenclatura visível no screenshot quando isso ajudar o leitor a localizar a opção.

Se a interface mudou:

atualizar texto e imagem.

# 268. Checklist terminológico

Antes de publicar:

- [ ] WordPress está capitalizado corretamente?
- [ ] WooCommerce está escrito corretamente?
- [ ] nomes de plugins e produtos estão corretos?
- [ ] Editor de Blocos e Editor do Site não foram confundidos?
- [ ] Gutenberg foi usado no sentido correto?
- [ ] FSE só aparece quando realmente necessário?
- [ ] tema não foi confundido com template?
- [ ] Multisite está usado de forma consistente?
- [ ] “site da rede” foi preferido a “subsite” quando adequado?
- [ ] staging foi explicado se o público exigir?
- [ ] termos em inglês foram mantidos apenas quando úteis?
- [ ] nomes de interface correspondem à versão atual?
- [ ] funções, arquivos e comandos permanecem literais?
- [ ] siglas foram explicadas quando necessário?
- [ ] nomes antigos de recursos não estão sendo usados como se fossem atuais?
- [ ] não variamos terminologia apenas para evitar repetição?

# 270. Regra final

> **Consistência dá sensação de domínio técnico. Precisão prova esse domínio.**

A PluginTema não precisa traduzir tudo.

Também não precisa escrever como documentação em inglês.

O objetivo é usar uma linguagem brasileira, natural e moderna, mantendo os nomes técnicos corretos o suficiente para que o leitor consiga:

- entender;
- pesquisar;
- localizar a opção;
- reproduzir o procedimento;
- aprofundar o assunto.
